## Resultado esperado

Los trabajos iniciados desde **Calendario** (Google/Outlook) y **Personas** (`/dashboard/person-research`, tanto **Registros PDL** como **Web pública**) actualizan automáticamente su estado general mediante SSE. `DossierJobsProvider` deja de consultar cada 3 segundos. Se conservan generación, cancelación, restauración de sesión, créditos, avisos y enlaces existentes.

Es una entrega independiente de S5.4: una sesión y un PR para S5.1. Esta sesión solo prepara documentación; no reclama las tareas de implementación.

**Ampliación del 2026-10-13:** Personas deja de ser solo una regresión genérica; ambas modalidades tienen casos de aceptación y pruebas obligatorios. El detalle de etapas se implementará en S5.4. `person_manual` usa jobs remotos y no debe confundirse con `corporate_manual`, que permanece para después.

## Preguntas resueltas antes de diseñar

| Pregunta | Respuesta y consecuencia |
|---|---|
| ¿Se construye el canal desde cero? | No. S4.8 ya aporta ruta, autenticación, stream y pruebas. Reutilizarlos |
| ¿Qué endpoint existe realmente? | `/dossier-generation-jobs/{job_id}/stream`; usarlo en lugar de las rutas previstas en el ADR antiguo |
| ¿Cómo llega la sesión al stream? | Bearer mediante fetch; el ADR elige `@microsoft/fetch-event-source`. No poner JWT en query string |
| ¿Todos los IDs actuales son del servidor? | No. El corporativo manual usa UUID local; excluirlo del stream en S5.1 |
| ¿El evento basta para actualizar el job? | Sí: los eventos generales contienen `serialize_job()`. No agregar un GET por evento |
| ¿Se elimina todo polling del dashboard? | Esta tarea retira solo el de jobs; notificaciones continúa bajo S5.2 |
| ¿Se implementa backoff aquí? | No. Dejar una interfaz clara para S5.3; controlar los reintentos implícitos de la librería |
| ¿Qué pasa si se corta la conexión? | Conservar el estado, informar la interrupción y permitir resincronización manual puntual |
| ¿Puede cerrarse B4 con S5.1? | No. Faltan S5.2, S5.3 y S5.4, además de la validación conjunta |
| ¿Qué dejó Felipe? | `progress.md`, entrada 2026-10-05: worker publica eventos, respaldo DB cada 10 s y frontend pendiente para DG |
| ¿PDL y Web pública tienen el mismo job? | Comparten el tipo `person_manual` y el transporte, pero cada ejecución conserva su modalidad. Sus procesos internos son diferentes y se detallan en la spec S5.4 |
| ¿S5.1 necesita nuevas etapas de backend para Personas? | No. El stream general existente ya cubre ambos recorridos; la instrumentación detallada se hace en el seguimiento backend de S5.4 |
| ¿Web pública ya busca en internet? | El código actual llama DeepSeek sin búsqueda en vivo; no interpretar los nombres históricos ni el booleano legado como prueba de búsqueda |

## Riesgos que el agente debe atender

| Riesgo | Prevención / evidencia |
|---|---|
| Bootstrap sobrescribe un job recién creado | Merge funcional y prueba de carrera |
| Bucle de streams al recibir eventos | Registro estable por ID y prueba con múltiples actualizaciones |
| Cierre de red interpretado como generación fallida | Estado de conexión separado del estado de job |
| Cancelación se pinta como fallo | Usar `data.status`, no solamente el nombre `job_failed` |
| React conserva callbacks de otra sesión | Identidad/epoch de suscripción, abort y limpieza comprobados |
| Secuencias reiniciadas se descartan como antiguas | Cursor por conexión; recuperación puntual explícita; replay robusto en S5.3 |
| La eliminación aparente del timer oculta otro polling | Aserción sobre llamadas HTTP, no solo búsqueda textual |
| Múltiples procesos/proxy degradan la inmediatez | Validar topología real; el bus actual es local al proceso. No prometer latencia entre procesos |
