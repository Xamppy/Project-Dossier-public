## Resultado esperado

Durante la generación desde **Calendario** (Google/Outlook) y **Personas** (`/dashboard/person-research`, **Registros PDL** y **Web pública**), el usuario distingue las operaciones en ejecución, completadas, omitidas y fallidas. Puede revisar contenido parcial válido aunque el informe no termine, y abrir el dossier final cuando realmente exista un resultado válido guardado.

Darío confirmó que quiere progreso real en vivo y que **el corporativo manual queda para una entrega posterior**. El plan no migra ese flujo a jobs ni cambia su API. Tampoco presenta una barra de progreso simulada como si fueran eventos del servidor.

## Qué cambia respecto al alcance anterior

Ampliación solicitada el 2026-10-13, que sustituye la restricción anterior a calendario:

- Personas deja de ser solo una regresión: PDL y Web pública tienen recorridos, etapas, parciales, estados de UI y pruebas propios.
- Calendario mantiene agentes corporativos y agrega detalle de sus investigaciones personales por asistente, cuando se ejecuten; cada persona recibe un scope independiente.
- El seguimiento backend incluye `stage_progress`, proyección pública de perfiles, modalidad/procedencia real, conservación de parciales en failed y snapshot por scope. Conserva `agent_progress` para agentes corporativos.
- Se amplían archivos y prompts de backend/frontend; criterios backend BE1–BE13 y frontend CA1–CA24. S5.1 se valida explícitamente para ambas modalidades personales, pero solo sobre estado general.
- Corporativo manual, S5.2 (notificaciones), S5.3 (reconexión automática) y S5.5 (renderizador JSON) siguen separados. No se incorpora un proveedor de búsqueda web ni se modifican reglas de cobro.

La inspección de `person_gemini_web_research.py` demuestra que la etiqueta actual **Web pública** corresponde a una llamada DeepSeek **sin búsqueda web en vivo**. El prompt y la UI deben representar esa operación: «Elaborando informe con IA», sin búsquedas ficticias ni fuentes atribuidas al flag legado gemini_google_search_used.

## Preguntas resueltas

| Pregunta | Respuesta |
|---|---|
| ¿Basta con los eventos existentes? | Para estado general de ambos módulos sí (S5.1); para S5.4 no. Calendario solo avisa fallos corporativos al terminar; Personas no emite etapas ni parciales |
| ¿S4.9 se puede aprovechar? | Sí: reutilizar los reducers, resultado detallado del grafo, fallos persistidos y pruebas existentes |
| ¿Un job completed significa resultado completo? | No: puede contener dossier válido con fuente fallida; separar éxito técnico y calidad parcial del resultado |
| ¿Un agente sin datos falló? | No necesariamente; cero coincidencias, fuera de alcance, caché y error son situaciones diferentes |
| ¿Se puede reconstruir éxito por ausencia en agents_failed? | No: también puede estar omitido o no existir metadata. El backend debe informar qué ocurrió |
| ¿Qué pasa con varias personas en una reunión? | Evaluar toda la lista `saved_dossiers.persons`, preservando el campo legado `person` |
| ¿El buffer SSE basta para recargar? | No: está limitado y se elimina al terminar. Se necesita snapshot recuperable y resumen final persistido |
| ¿Dónde se muestra? | Detalle de reunión y avisos, reutilizando CalendarDossierPreview; en Personas un panel de etapas y contenido de la ejecución seleccionada que persiste tras el terminal |
| ¿Qué idiomas aplican? | Siete según los tipos actuales: es, en, en-gb, pt, it, fr, de |
| ¿PDL y Web pública comparten etapas? | Comparten caché/finalización/persistencia, pero PDL hace enrich/search y síntesis con respaldo condicional; gemini_web llama análisis contextual sin consultar PDL |
| ¿Qué parcial personal es posible? | Perfiles PDL permitidos antes de síntesis; informe contextual solo después de que regrese la llamada completa. Con fallo previo a producir contenido, no hay parcial |
| ¿Un job personal failed obliga a ocultar todo? | No. Puede conservar perfiles útiles aunque falle el informe. Separa estado general, contenido disponible y dossier guardado |
| ¿El calendario usa el mismo wrapper que Personas? | No. Comparte run_person_research, pero tiene wrappers propios de caché y persistencia y modalidad por PERSON_RESEARCH_PROVIDER |
| ¿Cómo se distinguen sujetos/modalidades tras recargar? | Snapshot con scopes estables por sujeto y modalidad declarada por servidor, nunca el selector actual del formulario |
