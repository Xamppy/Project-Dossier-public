## Problema y evidencia

`frontend/src/providers/DossierJobsProvider.tsx` consulta cada 3 segundos los trabajos activos mediante `fetchDossierGenerationJob`. El servidor ya expone `GET /dossier-generation-jobs/{job_id}/stream` en `backend/src/dossier/api/dossier_stream_routes.py`; el worker publica estados y el stream espera esos eventos. La lectura periódica de PostgreSQL cada 10 segundos es un respaldo interno del servidor y no forma parte del sondeo que retira esta tarea.

Los trabajos de calendario y persona tienen un ID del servidor. El corporativo manual actual crea un `crypto.randomUUID()` local y ejecuta una petición HTTP directa: no puede abrirse un stream con ese identificador. Darío decidió dejar su migración para una entrega posterior; no es dependencia de la primera entrega de S5.4.

La tarjeta no fue legible desde la herramienta web en esta sesión. Se usa el título y las dependencias de `.harness/feature_list.json`, más la descripción facilitada por Darío. Los criterios siguientes son una propuesta verificable, no una transcripción de criterios remotos.

## Alcance

Incluye explícitamente los trabajos iniciados desde **Calendario** (Google/Outlook, `calendar_manual`) y **Personas** (`/dashboard/person-research`, `person_manual`) en sus dos modalidades: **Registros PDL** (`research_source: pdl`) y **Web pública** (`research_source: gemini_web`). Ambas modalidades de Personas ya usan `enqueuePersonResearch`, `async_mode: true` y un job del servidor. `person_manual` no es el flujo `corporate_manual` con UUID local.

Se implementan transporte SSE autenticado, integración en el proveedor, recuperación inicial, cancelación, limpieza de conexiones y conservación de resultados/toasts. S5.1 actualiza el **estado general** de los tres recorridos; no depende de instrumentar etapas internas de Personas para sustituir el polling. Esas etapas y sus parciales pertenecen a S5.4.

**Cambio respecto al borrador inicial (2026-10-13):** Personas pasa de una mención genérica/regresión a una matriz de aceptación obligatoria para PDL y Web pública. S5.4 se amplía también a Personas; Corporativo manual sigue excluido.

S5.2 conserva la responsabilidad sobre `NotificationsProvider`; S5.3, sobre reconexión automática con retroceso progresivo; S5.4, sobre presentación de agentes y resultados parciales; S5.5, sobre renderizado modular del dossier JSON. Ninguna se considera terminada por implementar S5.1.

## Contrato real que debe consumir

| Elemento | Comportamiento verificado en código |
|---|---|
| URL | `${getApiBaseUrl()}/dossier-generation-jobs/${jobId}/stream`; conservar el posible prefijo `/api` de la base |
| Autenticación | `Authorization: Bearer` mediante `getStoredAccessToken()`; token fuera de URL, logs y mensajes |
| Respuesta | HTTP 200 y `Content-Type` compatible con `text/event-stream` |
| `job_status` | `data` es el snapshot de `serialize_job()`, con `id`, `status`, `job_type`, resultado, créditos y fechas |
| `job_completed` | Mismo snapshot, normalmente `status: "completed"` |
| `job_failed` | Puede contener `status: "failed"` **o** `"cancelled"`; manda el estado del payload |
| Estados de job | `queued`, `running`, `completed`, `failed`, `cancelled` |
| `agent_progress` legado | Solo fallos corporativos del calendario al terminar; contiene `dossier_id` que hoy es, en realidad, el ID del job. No tratarlo como snapshot de job |
| Heartbeat | Comentario `: ping`, sin JSON de aplicación |
| ID de frame | Secuencia numérica por job, volátil; no es una versión persistente del resultado |
| Acceso | 401 sin sesión válida; 404 para inexistente o ajeno al usuario/organización |
| Vida del stream | Cierre terminal o corte de seguridad a los 600 segundos |
| Personas PDL y Web pública | Comparten `person_manual` y los eventos generales. La modalidad se almacena en `reunion_snapshot.person_request.research_source`, pero `serialize_job()` aún no la expone mientras corre. El resultado terminal incluye `filters_applied.research_source` |

Las URLs `/dossiers/{id}/stream` y `/events/live` del ADR histórico no son endpoints implementados en esta base. Esta spec registra esa diferencia; no ordena crearlos.

## Diseño

1. Crear un adaptador en `frontend/src/lib/dossier-job-stream.ts`. Usar `@microsoft/fetch-event-source`, elegido por ADR 0006, reutilizando las funciones de URL y token existentes. Fijar su versión y actualizar el lockfile al implementarlo. Validar en ejecución el JSON como `unknown`, el ID esperado y los campos obligatorios; un `as` de TypeScript no valida datos externos.
2. Separar el ciclo de conexión del estado de negocio. Un registro de suscripciones conserva, por job remoto activo, su `AbortController`, identidad de sesión y último cursor. Un cambio de créditos, idioma o toast no reabre la conexión. Los callbacks de una suscripción cerrada se ignoran.
3. Mantener la consulta inicial de jobs activos y las lecturas puntuales de IDs restaurados. Fusionarlas con el estado actual: una respuesta inicial tardía no puede borrar un job recién encolado ni revertir un estado terminal. No abrir streams para jobs terminales o IDs corporativos locales. Depurar IDs expirados/404 de la restauración.
4. Aplicar snapshots válidos conservando campos exclusivamente visuales como `toastDismissed`. Hacer idempotente la actualización y sincronizar almacenamiento desde el estado resultante, no desde una referencia atrasada. Un evento de agente nunca sustituye `job.result` ni el estado general.
5. Cerrar la conexión al completar, fallar, cancelar, desmontar o invalidar la sesión. Cancelar sigue usando la API existente; si la cancelación falla, conservar el job y mostrar el error. No confundir abortar la lectura con cancelar el trabajo del servidor.
6. Ante fallo de transporte, conservar el último resultado y marcar la conexión como interrumpida. No cambiar el job a `failed`: una conexión rota no demuestra una generación fallida. Ofrecer una recuperación manual que obtiene un snapshot REST una vez y abre un nuevo stream, si el job sigue activo.
7. S5.1 controla explícitamente los reintentos de la librería: sin bucle automático ni fallback periódico. Configurar los errores para detener esa suscripción y evitar reaperturas ocultas al cambiar de pestaña; mantener la conexión mientras la pestaña esté oculta mediante la opción prevista por la librería. S5.3 sustituirá esa política por la reconexión acordada, con pruebas propias. La resiliencia automática es un requisito separado antes de declarar lista la experiencia de producción.
8. Si se acepta una nueva conexión tras una recuperación, no descartar ciegamente IDs menores al cursor anterior: el bus puede reiniciarse. Para la recuperación manual de S5.1, usar el snapshot puntual y abrir sin cursor histórico. Reservar el replay con `Last-Event-ID` y sus límites para S5.3.
9. Parametrizar la integración sobre Calendario, Personas/PDL y Personas/Web pública. Preservar `force_refresh`, `replace_dossier_id`, idioma y campos enviados por `enqueuePersonResearchJob`. Mientras un job restaurado no informe modalidad, usar el estado general y su etiqueta del servidor; no deducirla del selector actual del formulario ni del booleano legado `gemini_google_search_used`. S5.4 agregará metadata explícita al snapshot.

El ADR 0006 propone fallback a sondeo como estrategia final. No se introduce en esta entrega: debe reconciliarse expresamente en S5.3 con el objetivo de retirar consultas periódicas, sin activar dos mecanismos de actualización a la vez.
