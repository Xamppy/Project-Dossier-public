# S1.9 · Modelo común de registro corporativo (UK / US / EU)

- **Tarea:** S1.9 · [tarjeta](https://trello.com/c/mMpvfTj3)
- **Responsable:** FO
- **Brecha:** B2 (Registros Europeos)
- **Depende de:** S0.12 (arquitectura del agente europeo, acordada)
- **Bloquea:** S2.1 (agente europeo), S2.3 (adaptar agentes UK/US al modelo común)
- **Estado:** propuesta

## Problema

Hoy no existe un modelo de datos para "registro corporativo". `build_uk_corporate_context_markdown`
y `build_us_corporate_context_markdown` (`services/corporate_registry_context.py:648,708`) vuelcan
el JSON crudo de Companies House y de SEC EDGAR directo en Markdown, que luego lee el LLM. No hay
ninguna estructura intermedia: cada fuente tiene su propio vocabulario (`company_number` vs `CIK`
vs `SIREN/SIRET`), sus propios nombres de campo, y no hay lugar común donde parar antes de la
síntesis.

ADR 0003 (fuente de registros europeos) ya nombra la solución: **normalizar Francia y Alemania al
"esquema unificado `RegistroCorporativo` interoperable con Companies House (UK) y SEC EDGAR (US)"**.
Esta tarea es esa normalización: define el esquema, no lo conecta todavía a los agentes existentes
(eso es S2.3) ni implementa el cliente europeo (eso es S1.8/S2.1).

## Alcance

**Incluye:**
- Un modelo Pydantic `RegistroCorporativo` que las cuatro jurisdicciones objetivo (`uk`, `us`,
  `fr`, `de`) puedan poblar sin forzar campos que no tienen.
- Submodelos para domicilio, directivos y presentaciones/filings, con los campos que **ya**
  aparecen en las fuentes decididas (ADR 0003): Companies House, SEC EDGAR, API Recherche
  d'entreprises (Francia) y Handelsregister/OffeneRegister (Alemania).
- Un campo de escape (`datos_brutos`) para no perder información de la fuente mientras S2.3 decide
  qué migrar a campos estructurados y qué se sigue citando como JSON crudo.

**No incluye:**
- Adaptadores que conviertan las respuestas reales de cada API al modelo (S2.1, S2.3).
- Cambiar `corporate_dossier_graph.py` para que use el modelo en vez de Markdown (S2.2, S2.3).
- El esquema JSON del dossier ejecutivo completo (`dossier_data`, S0.9/S4.1): `RegistroCorporativo`
  es una pieza que ese esquema podrá referenciar, no lo reemplaza.

## Diseño

Ubicación: `backend/src/dossier/schemas/corporate_registry.py`, junto al resto de esquemas Pydantic
compartidos (`schemas/person_research.py`, `schemas/dossier_generation.py`).

```python
class JurisdiccionRegistro(str, Enum):
    uk = "uk"
    us = "us"
    fr = "fr"
    de = "de"


class DomicilioRegistrado(BaseModel):
    calle: str | None = None
    localidad: str | None = None
    region: str | None = None
    codigo_postal: str | None = None
    pais: str | None = None


class Directivo(BaseModel):
    nombre: str
    cargo: str | None = None
    fecha_nombramiento: str | None = None  # ISO 8601 si la fuente lo entrega


class Presentacion(BaseModel):
    """Un ítem de filing history (CH) o de submissions (SEC), o su equivalente europeo."""
    fecha: str | None = None
    tipo: str | None = None
    descripcion: str | None = None
    url: str | None = None


class RegistroCorporativo(BaseModel):
    jurisdiccion: JurisdiccionRegistro
    fuente: str  # "companies_house" | "sec_edgar" | "recherche_entreprises" | "handelsregister"
    identificador_registro: str  # company_number / CIK / SIREN-SIRET / HRB-HRA
    razon_social: str

    estado: str | None = None          # company_status / état / Status
    forma_juridica: str | None = None  # type / nature_juridique / Rechtsform
    fecha_constitucion: str | None = None

    domicilio: DomicilioRegistrado | None = None
    codigos_actividad: list[str] = []  # SIC (UK) / APE-NAF (FR)
    directivos: list[Directivo] = []
    presentaciones: list[Presentacion] = []

    url_fuente: str | None = None
    consultado_en: datetime | None = None
    datos_brutos: dict[str, Any] | None = None
```

### Mapeo de campos por fuente (referencia para S2.1 / S2.3, no implementado aquí)

| Campo común | Companies House (UK) | SEC EDGAR (US) | Recherche d'entreprises (FR) | Handelsregister (DE) |
|---|---|---|---|---|
| `identificador_registro` | `company_number` | `CIK` | `siren` / `siret` | número HRB/HRA |
| `razon_social` | `company_name` | `name` en submissions | `nom_complet` | razón social del registro |
| `estado` | `company_status` | n/a directo (se infiere) | `etat_administratif` | Status |
| `forma_juridica` | `type` | n/a | `nature_juridique` | Rechtsform |
| `fecha_constitucion` | `date_of_creation` | n/a | `date_creation` | variable por Land |
| `domicilio` | `registered_office_address` | `addresses.business` | `siege` | domicilio del registro |
| `directivos` | requiere endpoint de officers aparte (no se consulta hoy) | n/a | `dirigeants` | directores (según ADR 0003) |
| `presentaciones` | `filing_history.items` | `filings.recent` | n/a directo | n/a directo |

Esta tabla es la que S2.1 y S2.3 van a necesitar; se deja aquí para no repetir la investigación.

## Criterios de aceptación

- [ ] **CA1** — `RegistroCorporativo` se puede instanciar con solo los cuatro campos obligatorios
  (`jurisdiccion`, `fuente`, `identificador_registro`, `razon_social`); todo lo demás tiene default.
- [ ] **CA2** — Las cuatro jurisdicciones del alcance firme (`uk`, `us`, `fr`, `de`) son valores
  válidos de `JurisdiccionRegistro`; cualquier otro valor falla la validación.
- [ ] **CA3** — `domicilio`, `directivos` y `presentaciones` aceptan datos estructurados reales
  (forma de las cuatro fuentes de la tabla de mapeo) sin perder campos.
- [ ] **CA4** — El modelo serializa a dict/JSON (`model_dump`) sin errores, para poder embeberse
  luego en `dossier_data` (S4.1) o citarse desde Markdown.
